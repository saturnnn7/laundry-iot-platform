# UC-08 Start a session at the machine with a code

Actors: Resident, Device. Stories: US-15 to US-18, US-27.

## Main flow
1. The resident presses the button on the machine. The device sends the event `buttonPressed`.
2. The platform creates a session request and a 6-character code (hashed, valid 60 seconds) and sends `showCode`; the device displays it.
3. The resident enters the code in the app or API (`POST /sessions/claim`). The platform checks the attempt limit, the code and the membership.
4. If the resident has a booking or hold for this machine covering now (claim window: 5 minutes before the start to 10 minutes after), it is used. Otherwise the session is a walk-up.
5. The platform sends `unlock` with the resident's display name; the device unlocks and shows the name.
6. The resident chooses a program (`POST /sessions/{id}/start`). The platform checks the walk-up fit rule, calls the payment port and sends `start`.
7. The device runs the cycle and reports phase `running`; UC-06 ends the session.

## Alternatives
- The machine is OutOfService, busy, or reserved for someone else: the platform sends `showMessage` instead of a code.
- Code wrong: `code-invalid`. Code older than 60 seconds: `code-expired`; press the button again. More than 5 failed attempts per minute for a user: `too-many-attempts`.
- A booking holder arrives while the previous session still runs: `machine-busy`; the no-show timer pauses until the machine is free.
- Walk-up program does not fit before the next reservation: `program-not-fit`; the resident may choose a shorter program.
- A command is not acked within 10 seconds: retried twice, then `command-failed`.

## Rules
- The device never creates or checks codes and sends no approval.
- Walk-up fit rule: now + occupied(program) must be at or before the start of the next reservation on that machine.
- Commands and acknowledgements follow docs/api/contracts/README.md.
